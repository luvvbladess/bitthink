# Дешёвый режим генерации больших документов (docgen)

**Дата:** 2026-09-15
**Статус:** утверждено к реализации

## Задача

Отдельный режим чата: пользователь даёт промпт, система генерирует документ
на основе уже загруженных в чат исходников. Ключевые требования:

- итоговый документ может быть очень большим (тысячи страниц), генерируется
  за один запуск как единый файл;
- исходники, на основе которых пишется документ, тоже могут быть очень
  большими (тысячи страниц);
- результат — .docx файл, без промежуточного показа черновика в чате;
- пользователь не ждёт синхронно: это фоновая задача с прогрессом;
- модель для каждого раздела выбирается по стоимости: дешёвая по умолчанию,
  эскалация на более сильную только для сложных разделов;
- это отдельная задача, не привязанная к конкретному прошлому проекту
  (ИТТ/буксир) — общий режим для любых документов.

## Приём .zip архивов

Источник может быть загружен одним .zip-архивом (много документов внутри).
Это общее улучшение точки загрузки, а не что-то специфичное для docgen —
чинится один раз в `backend/app/api/documents.py::upload_document`, поэтому
архивом смогут пользоваться и остальные режимы (Auto, Director и т.д.), не
только docgen.

- `ext == ".zip"` обрабатывается отдельной веткой до проверки
  `DOCUMENT_EXTENSIONS` (архив как таковой в этот список не входит).
- Новая функция `_extract_zip_documents(contents: bytes) -> list[tuple[str, str]]`
  в `document_parser.py`: разворачивает `zipfile.ZipFile` в памяти,
  пропускает директории и служебные записи (`__MACOSX/`, `.DS_Store`),
  для каждой записи с расширением из `DOCUMENT_EXTENSIONS` вызывает уже
  существующий `extract_text_from_file(entry_bytes, entry_name)` —
  никакой новой логики парсинга форматов, только маршрутизация по архиву.
- На выходе — список `(имя_файла_внутри_архива, текст)`. Каждый файл
  сохраняется через `repo.add_document` отдельной записью
  (`f"{archive_name}/{inner_name}"`), как если бы пользователь загрузил их
  по одному — downstream-код (в т.ч. `_extract_source_chunks` в docgen)
  не меняется, он и так работает с произвольным числом системных
  сообщений о документах.
- В чат добавляется одно сообщение-вложение вида «archive.zip (N файлов)»,
  а не N отдельных карточек.
- Лимит размера — тот же `max_size` (20 МБ на присланный файл), что уже
  действует для документов; распакованные файлы дополнительно проходят
  через существующие per-file лимиты парсеров (`MAX_EXTRACT_CHARS` и т.д.).

## Компоненты

Новый модуль `backend/app/bot_core/docgen_router.py`, по конвенциям
существующих `hybrid_router.py` (выбор модели по сложности) и
`director_router.py` (параллельные раунды, капы, фоновый прогресс).

### `_extract_source_chunks(messages) -> list[Chunk]`

Источник текста — те же системные сообщения о загруженных документах, что
уже собирает `hybrid_router._format_chat_history` /
`director_router._extract_document_context` (ищутся по маркерам
`"документ для контекста"` / `"предоставил документ"`). Текст этих
сообщений уже приходит от `document_parser.py` с постраничными маркерами
(`--- Страница N ---` для PDF, `[Lx]` для уровней списков DOCX). Функция
режет текст по этим маркерам на чанки:

```python
@dataclass
class Chunk:
    id: int
    title: str   # первая содержательная строка чанка, до 120 символов
    text: str    # содержимое чанка, до ~3000 символов
```

Если маркеров нет (например, простой .txt), чанки нарезаются по абзацам с
целевым размером ~3000 символов.

### `_select_relevant_chunks(section_brief: str, chunks: list[Chunk], top_k: int = 6) -> list[Chunk]`

Чистый Python, без LLM и без внешних библиотек:

1. токенизация `section_brief + section_title` и `chunk.title + chunk.text`
   (нижний регистр, разбиение по не-буквенным символам, стоп-слова не
   нужны — простое пересечение множеств токенов длиной от 3 символов);
2. вес чанка = размер пересечения токенов, взвешенный вхождениями в
   `chunk.title` (заголовок совпадений весит x3);
3. возвращает `top_k` чанков с ненулевым весом, отсортированных по весу.

Если ни один чанк не набрал вес — берутся первые `top_k` чанков по порядку
(чтобы раздел не остался вовсе без контекста).

### `_plan_outline(user_text: str, chunks: list[Chunk], user_id: int) -> list[Section]`

Один вызов сильной модели (`gpt-5.6-terra`, как в `director_router.PLANNER_MODEL`).
В промпт идут **только заголовки чанков** (`chunk.id: chunk.title`), не
полный текст — поэтому вызов остаётся дешёвым и коротким даже при
исходниках на тысячи страниц.

```python
@dataclass
class Section:
    id: int
    title: str
    brief: str          # что должно быть в разделе, 1-3 предложения
    complexity: str      # "simple" | "complex"
```

Модель возвращает JSON-массив `Section`. Как и в `hybrid_router.split_query_into_tasks`,
любая ошибка парсинга — не исключение, а безопасный фолбэк (один раздел
"Документ" с `complexity=complex`, если план вообще не удалось построить).

### `_write_section(section: Section, chunks: list[Chunk], user_id: int) -> str`

Возвращает markdown-текст раздела (без обёртки в `##`, заголовок добавляет
сборщик).

Выбор модели — по образцу `hybrid_router.execute_subtask`:
- `complexity == "simple"` → `gpt-5.6-luna` (дефолт, самое дешёвое);
- `complexity == "complex"` → `deepseek-v4-pro` (если есть ключ, иначе
  `gpt-5.6-terra`) — как уже сделано для сложных подзадач в Auto-режиме.

В промпт раздела идут: `section.brief`, релевантные чанки из
`_select_relevant_chunks`, и **хвост предыдущего раздела** (последние
~500 символов уже написанного текста), чтобы соседние разделы не
противоречили друг другу по терминологии и не повторяли вводные фразы —
дёшево (несколько сотен токенов), но ощутимо снижает нестыковки между
разделами, сгенерированными параллельно в одной пачке.

### `run_docgen_job(user_id, conversation_id, messages, user_text) -> None`

Оркестратор фоновой задачи. Использует существующий
`backend/app/services/generation_hub.py` — новый движок задач не нужен:

1. `chunks = _extract_source_chunks(messages)`
2. `outline = await _plan_outline(user_text, chunks, user_id)` (обрезается
   капом `MAX_SECTIONS`)
3. Разделы пишутся пачками по `MAX_PARALLEL_SECTIONS` (по аналогии с
   `director_router.MAX_PARALLEL_PER_ROUND`) через `asyncio.gather`;
   после каждой пачки — `senders.send_status(f"Раздел {done} из {total}")`.
4. Сбой одного раздела не прерывает job: текст раздела заменяется на
   `f"[Не удалось сгенерировать раздел: {err}]"`, генерация продолжается —
   инженер увидит явную пометку при вычитке, а не тишину.
5. Сборка: `"\n\n".join(f"## {s.title}\n\n{text}" for s, text in ...)`.
6. `docx_bytes = docx_generator.convert_markdown_to_docx(full_markdown)`
   (существующая функция, без изменений).
7. `await senders.send_file(f"{doc_title}.docx", docx_bytes)`.

Ошибки на этапе плана (шаг 2) — фатальные для job: `send_status` с текстом
ошибки, файл не отправляется (частично собранный документ без структуры
хуже отсутствия документа).

### Точка входа в чате

В `backend/app/bot_core/handlers/core.py`, рядом с диспетчеризацией
`auto`/`director`/`correspondent`/`studio` (строки ~399-461): новая ветка
`elif model == "docgen":`, которая не ждёт `result`, а сразу стартует
`generation_hub.hub.start_task(user_id, conversation_id, run_docgen_job(...))`
и возвращает пользователю подтверждение о старте фоновой генерации —
аналогично тому, как уже работают долгие job'ы через `generation_hub`.

## Ограничения стоимости и масштаба

Капы по образцу `director_router` (`MAX_ROUNDS`, `MAX_EMPLOYEES`):

- `MAX_SECTIONS` — верхняя граница числа разделов в одном документе;
- `MAX_PARALLEL_SECTIONS` — размер пачки параллельных вызовов (ограничивает
  всплеск запросов к провайдерам);
- `MAX_CHUNK_CHARS_PER_SECTION` — сколько символов исходников подмешивается
  в один раздел (по аналогии с `director_router.MAX_RESULT_CHARS_IN_PROMPT`).

Конкретные числа подбираются на этапе реализации по факту (тест на реальном
большом документе), в спеке не фиксируются.

## Тестирование

Нетривиальная логика — чанкинг и ранжирование чанков по ключевым словам —
получает один `test_docgen.py` с `assert`-проверками на синтетическом
многостраничном тексте (без фреймворков, без моков LLM):

- `_extract_source_chunks` корректно режет текст с маркерами страниц на
  ожидаемое число чанков;
- `_select_relevant_chunks` находит чанк, явно релевантный по ключевым
  словам, выше нерелевантных.

Полный прогон генерации (LLM-вызовы) вручную на реальном документе —
автотестом не покрывается.

## Вне рамок этой спеки

- Синхронный/чатовый предпросмотр черновика — не нужен по требованиям.
- Retrieval через embeddings/векторный поиск — сознательно не используется
  (лишняя зависимость и стоимость ради задачи, которую решает лексический
  подбор).
- UI-кнопка выбора режима "docgen" на фронтенде — отдельная, чисто
  фронтенд-часть работы плана реализации.
