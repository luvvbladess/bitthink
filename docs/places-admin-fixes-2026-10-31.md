# Подбор заведений и загрузка админки — 31.10.2026

## Причины и границы диагностики

Короткий запрос о ресторанах мог идти через light research: один сотрудник, общий лимит 2 поисков / 3 чтений, завершение после наличия хотя бы одной ссылки без проверки цены. Это позволяло свести подбор к одному обзору. Уточнение стоимости не всегда распознавалось как продолжение задачи о местах.

Позднее повторные замеры воспроизвели 6.4–7.8 секунд холодного открытия: HTML/TLS около 1.3 с, основной JS до 3.6 с, чанки админки до 1.2 с. Запросы API в изолированном браузерном замере были заглушками; прямой серверный замер реального API приведён ниже. Медленная загрузка ресурсов воспроизвелась при быстрых API; это указывает на сетевую часть, без доказательства конкретного внешнего узла. Измерения на production до изменений: HTML около 92 мс, авторизованный /admin/users 8–28 мс, /admin/stats 7–11 мс. Чистый Playwright с реальными публичными assets, синтетическим администратором и заглушками API: холодный показ списка 880 мс. Это не измерение реального устройства пользователя и не доказательство отсутствия временной сетевой задержки.

## Изменения

- Классификация подбора заведений и связанных уточнений использует только исходные пользовательские сообщения из текущей истории. Смена темы, запрет интернета и рецепты отделены от поиска заведений.
- Оркестратор выполняет два независимых направления (меню/цены и карты/отзывы), затем зависимую проверку подходящих кандидатов. Дорогие и неподтверждённые по цене места не должны становиться основной рекомендацией «недорого». Лёгкое завершение по одной ссылке для этого сценария выключено.
- Бюджет такого запроса до 8 разных поисков / 18 чтений на ход, с общими дедупликацией и денежным ограничением. Остальные запросы сохраняют прежние лимиты. Целевое число вариантов — ориентир при достаточных данных, не разрешение выдумывать или заполнять список дорогими местами.
- Инструкции требуют сопоставлять конкретный филиал на картах с официальным меню, ценой нужного блюда и реалистичного заказа. Поисковая выдача и общий обзор не приравниваются к прочитанной карте. Блокировки карт должны оставаться явно обозначенным пробелом. Нового внешнего Maps API не подключалось.
- Оболочка и страница админки загружаются параллельно; ссылки в меню умеют предварительную загрузку. Ненужная предварительная загрузка настроек/биллинга при открытой админке отключена. Вложенная граница ожидания сохраняет заголовок и навигацию; список кэшируется на 15 с, статистика на 30 с. Полномочия по-прежнему проверяются сервером на каждом запросе.

## Проверки

Прошли выбранные backend-наборы для выбора мест, research, intent, search budget, hardening/economy, followup evidence и provenance/speed. Проверены исходный запрос со скриншота, сохранение СПб/центра при жалобе на цену, изоляция смены темы и запрета сети, обязательный этап повторной проверки, ограничение расхода.

Frontend: TypeScript и production build; браузерный прогон production build с искусственной задержкой модуля статистики 900 мс: оболочка остаётся видна, список не запрашивается заново при быстром возвращении, 390px без переполнения страницы и ошибок renderer. Локальный холодный показ на synthetic API — 302 мс; его нельзя напрямую сравнивать с сетевым production-замером. Снимок: C:/Users/vertu/AppData/Local/Temp/bitthink-admin-mobile.png.

Полный платный прогон модели с настоящей подборкой ресторанов не выполнялся: тесты подтверждают маршрутизацию и инструкции, а не гарантированную полноту будущего ответа. Доступность меню и карт зависит от источников.
