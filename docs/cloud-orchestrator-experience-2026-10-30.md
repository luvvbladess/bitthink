# Облачный Оркестратор: понятный ход работы и развитие

## Реализовано в этом изменении

Статус описывает действие для пользователя, а не устройство исполнителя. Примеры:

| Было | Стало |
| --- | --- |
| Исследую задачу | Разбираю задачу · Определяю нужный результат и порядок работы |
| Запускаю N сотрудников | Работаю над N частями задачи параллельно · Затем объединю результаты |
| Полное внутреннее задание сотрудника | Короткое описание работы: подбираю информацию / подготавливаю документ / сопоставляю данные |
| Python /рабочая/папка/script.py | Обрабатываю данные для задачи · Выполняю подготовленный сценарий |
| pip с перечнем пакетов | Подготавливаю инструменты · Они нужны для обработки данных и сборки файлов |
| Имя файла без глагола | Читаю материалы задачи · Имя файла |
| Внутренняя команда или HTTP-запрос | Выполняю действие на подключённом сервере / Обращаюсь к подключённому сервису |
| Пишу ответ | Собираю итоговый ответ · Объединяю выводы и подготовленные файлы |

Построение проекта отдельно показывает подготовку инструментов, сборку, запуск проверок, проверку отображения и упаковку. Эти статусы возникают при фактическом вызове соответствующего инструмента; они не являются сообщением о его успешном завершении. Имена внутренних ролей и полные задания не передаются в ленту. Для файлов показывается короткое имя вместо пути рабочей среды.

На интерфейсе заголовок действия и пояснение разделены. Длинное имя файла переносится, а не скрывается многоточием. Старая сохранённая лента с Python/pip/сотрудниками также получает понятные подписи. Фоновые задачи показывают последнее действие и в беседе, и в списке поручений; технические теги не отображаются.

История называется «История действий». Предыдущие записи отмечены нейтрально: смена статуса не доказывает успех, особенно при параллельной работе. Возврат к той же операции после правки снова виден в ленте; подряд идущие дубликаты подавляются. Число действий не выдаётся за процент готовности. Таймер подписан «в этом окне», потому что он не измеряет серверное время после закрытия вкладки.

Для облачного Оркестратора есть пояснение, что можно закрыть вкладку и вернуться в эту беседу. Продолжение, пауза, уточнение задания, расписания, сохранённые шаги и память проекта уже существуют; они не считаются новыми функциями этого изменения.

## Полезности следующего этапа — предложения

### 1. «Как я понял задачу»

В начале большого поручения коротко показать требуемый результат: что получить, из каких материалов, в каком формате. Сразу доступны «Уточнить» и «Продолжить работу». Основа — сохранённый план задачи, а не отдельный декоративный текст. Для обычного задания не вводить обязательное подтверждение: пользователь уже поручил его выполнить.

Польза: заметить неверно понятый объём до долгой работы. Проверка: изменение формата не теряет вложения, а выполняющийся вызов не объявляется мгновенно изменённым.

### 2. «Уже готово»

Небольшой список фактически созданных результатов прямо под текущим действием. Например, готовая таблица доступна в предпросмотре, пока отчёт ещё собирается. Только реальные сохранённые файлы, их версии и ошибки проверки. Сценарий промежуточных документов уже есть на сервере — развитие состоит в явном показе этих результатов и их состояния.

Польза: можно использовать часть результата, не ожидая весь комплект. Проверка: незавершённый файл не помечается готовым; открытая старая версия не заменяется незаметно.

### 3. «Повторить с новыми данными»

Сохранить успешное поручение как личный сценарий: заменить исходные файлы или ссылки, выбрать период и запустить снова. В отличие от существующего повтора задания, пользователь явно видит, какие данные будут заменены, какие правила сохранятся и какой формат результата ожидается.

Польза: еженедельные отчёты, сравнение новых прайсов, обработка очередного договора. Проверка: исходные документы предыдущего клиента не переходят в новое поручение скрыто.

### 4. «Что изменилось с прошлого раза»

Для повторяющихся облачных заданий показывать изменения относительно последнего успешного запуска: новые предложения, изменившиеся условия, новые документы. При сбое источника показывать пробел, а не «изменений нет». Уведомления о завершении/изменениях включаются пользователем; не рассылать пустые отчёты по умолчанию.

Польза: пользователь читает изменения вместо повторного большого отчёта. Проверка: сравниваются совместимые версии данных с датами и источниками; ошибка чтения не трактуется как исчезновение товара или события.

### 5. «Почему задача остановилась»

Единый понятный экран остановки: что уже сохранено, чего не хватает и какое действие продолжит работу. Например: нужен конкретный файл, истёк доступ к почте или закончился доступный лимит. Продолжение опирается на существующие контрольные точки и правила внешних действий, не запускает всё с начала.

Польза: длинное задание не превращается в тупик с надписью «Ошибка». Проверка: повтор не дублирует отправку письма, публикацию или другое внешнее действие.

## Приоритет

После понятных статусов: сначала «Как я понял задачу» и «Уже готово», затем личные повторяемые сценарии. Расписания и новые режимы не нужны сами по себе — ценность в понятном, проверяемом результате и возможности использовать его с телефона.

## Проверка изменения

12 выбранных серверных тестов: подписи инструментов, отсутствие внутренних команд и путей, повторная операция после правки, передача типа стадии из директора и сохранение различных поисковых запросов. Три новых сценария Chromium с подменённым API: лента на 320/1440 px, раскрытие истории, перенос длинного имени, старые статусы и последнее действие фоновой задачи. Отдельно проверен существующий сценарий постановки облачной задачи, повтора после ошибки, паузы и продолжения. TypeScript-проверка прошла. Живые платные задания и физические телефоны в этой проверке не использовались.

Изменения в исходниках; на рабочий сайт не опубликованы.

Уточнение: названия инструментов не являются пользовательскими статусами. Для `swarm_read`, `swarm_publish`, `swarm_send` добавлены описания «Сверяю промежуточные результаты», «Передаю результаты для дальнейшей работы», «Согласовываю детали выполнения задачи». Старые записи с техническими именами также преобразуются при отображении. Неизвестное внутреннее имя получает нейтральное описание действия. Облачные события совместной работы не выводят внутренние роли исполнителей. Проверено 15 серверными тестами и 5 браузерными сценариями скрытия названий в карточке фоновой задачи и списке поручений; TypeScript-проверка прошла.

Итоговая проверка после очистки прежних подписей: 18 серверных тестов прошли (включая маршруты директора и сохранение параллельной работы), 4 браузерных сценария прошли, производственная сборка успешна. Механическая проверка интерфейса не выявила нарушений.
