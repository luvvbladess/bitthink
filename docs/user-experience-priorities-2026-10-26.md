# Приоритеты пользовательского опыта BitThink

Оценка основана на текущем коде, последних пользовательских примерах и проверках выпуска. Это список предложений; перечисленные ниже изменения ещё не реализованы. Нового наблюдения за действиями реальных пользователей в рамках этого обзора не проводилось.

## Общая картина

Уже есть сохранение черновиков и вложений, история и поиск бесед, корзина, фоновые задачи, проекты, версии результатов, экспорт, память и контекстные продолжения. Повторно создавать эти возможности не требуется. Наибольшая польза следующего этапа — в понятном результате и надёжности полного пути пользователя.

Последние инциденты показывают три разных пробела: одинаково выглядящие действия делали разное; проверка источников могла обнулить полезный ответ; перенос генерации в другой процесс разорвал доступ к читателю магазинов. Успех отдельных компонентов не гарантировал успех пользовательской задачи.

## Предлагаемый порядок

### 1. Сквозные проверки реальных маршрутов — до следующего расширения

Сейчас есть обширные серверные тесты и браузерные сценарии с подменёнными API. Дополнить их проверкой связки браузер → API → очередь → отдельный исполнитель → читатель → сохранённый результат. Контролируемый читатель должен работать отдельным процессом, а не разделять память с тестом API.

Обязательные истории: покупка с несколькими типами цены; документ из вложения с экспортом; презентация с последующим редактированием; перезагрузка во время ответа; остановка; повтор после разрыва без дубля; мобильный ввод с клавиатурой. Ошибки из пользовательских примеров добавлять как обезличенные воспроизводимые случаи.

Критерий: выпуск проверяет получение результата, а не только готовность контейнеров и появление текста. Для нескольких процессов можно использовать существующий Playwright; его официальный механизм поддерживает запуск нескольких серверов и фоновых процессов: https://playwright.dev/docs/test-webserver#multiple-web-servers.

### 2. Единый формат полезного ответа

Для выбора: короткий вывод → конкретные варианты → решающие различия → существенное ограничение. Для работы с файлами: результат → скачать/изменить → что осталось уточнить. Историю поиска и технические причины не смешивать с основным выводом.

Критерий: первая часть ответа отвечает на исходный вопрос; недоступность одного магазина не отменяет остальные варианты. Фраза об ограничении указывает конкретный пробел, например «доставка зависит от города», вместо общего «данные не подтверждены». Прочитанная страница сама по себе не обозначается как гарантия достоверности всех выводов.

### 3. Структурированные предложения при подборе покупок

Чтение цен уже восстановлено. Следующий шаг — хранить различия между обычной ценой, скидкой по карте, старой зачёркнутой ценой, платежом рассрочки, доставкой и пошлиной. У каждого поля нужны исходная подпись, предложение/вариант товара и момент получения. Не назначать неизвестной сумме тип по догадке модели.

На интерфейсе показывать компактное предложение: точная модель/память/состояние, магазин, цена с условиями, ссылка. Действия: обновить, сравнить, посмотреть условия. Не создавать для этого ещё один отдельный режим.

Критерий: месячный платёж не становится ценой телефона, цена другой комплектации не попадает в сравнение, неизвестная итоговая стоимость не показывается как установленная.

### 4. Меньше выбора внутреннего режима

Автоматический поиск и предложения переключить режим уже реализованы. Доработать продолжение после предложения: сохранить исходное задание и файлы, переключить подходящий маршрут и явно показать, нужно ли ещё действие пользователя. Обычному пользователю достаточно понимать, какой результат он получит и есть ли существенное ограничение тарифа/расхода.

Внутренний Creator-only режим Документов не должен выглядеть как непонятная публичная функция с замком. Продвинутый выбор моделей оставить доступным по запросу, а основной путь строить вокруг задач. Дорогие длительные задания не запускать незаметно.

Критерий: новый пользователь получает ответ или создаёт доступный ему результат, не изучая различия между моделями и исполнителями.

### 5. Обратная связь именно по результату

В проверенных элементах ответа не найдено пользовательской оценки полезности. Добавить небольшое действие «Не помогло» с причинами: не ответил на вопрос, неверные данные, не получил файл, долго, другое. Можно предложить целевое исправление без повторного ввода всего запроса.

Сохранять идентификатор операции и выбранную причину; отправку текста переписки на разбор делать отдельным понятным действием пользователя. Не считать отсутствие ошибки сервера доказательством полезности ответа.

Критерий: видны наиболее частые причины неудачи и доля исправленных ответов. Проблемы не приходится обнаруживать исключительно по скриншотам в разработческом чате.

### 6. Следующее действие над уже полученным результатом

Контекстные подсказки уже есть, но значительная часть задаётся правилами по словам и режиму в `followUps.ts`. Развивать их на основе фактически созданного объекта: изменить конкретный файл, сделать короткую версию отчёта, обновить выбранные предложения, открыть текущую версию презентации. Версии и редактирование проектов уже существуют — нужно сделать их легче обнаружимыми из ответа.

Критерий: продолжение относится к текущему результату, сохраняет параметры и не создаёт новый полный результат без необходимости. На телефоне основные действия доступны без поиска в нескольких меню.

### 7. Прогресс и метрики завершения задачи

Фоновые задачи, остановка и технические метрики уже существуют. Развивать информативность: получен файл, извлечён текст, найдены предложения, получены цены, сохранён результат. Числа показывать только из событий выполнения; не придумывать процент готовности или срок.

Текущие метрики `experience.py` измеряют задержки и соединение. Дополнить агрегатами завершения: пригодный результат, экспорт, исправление ответа, отказ из-за внешнего источника. Сначала собрать исходные значения, затем ставить числовые цели; проценты улучшения пока не обещать.

## Первый пакет

Приоритет первого пакета: сквозная надёжность, ясная структура ответа и типизированные цены. Они прямо связаны с уже встреченными проблемами. Следующий пакет: обратная связь и продолжение работы с результатом. Масштабную смену визуального стиля, новые режимы и миграцию стека в этот план не включать без отдельной подтверждённой необходимости.
