# React и Next.js: применять по задаче

Основано на Vercel React Best Practices, MIT; версия, исходные файлы и контрольные суммы — ../SOURCE.json. Это дополнение к code, а не требование заменить стек пользователя на React или переписать готовый проект.

1. Сначала воспроизведи медленный пользовательский сценарий и проверь сборку. Не обещай проценты ускорения без измерения.
2. Независимые запросы запускай параллельно; зависимые оставь последовательными. Не создавай водопад запросов из-за расположения await. Пример: react-async-parallel.md.
3. Тяжёлый редактор, экспорт или график загружай при открытии соответствующей функции. Для Next.js есть next/dynamic, для обычного React — React.lazy/import(). Не добавляй библиотеку ради одного эффекта. Пример: react-bundle-dynamic-imports.md.
4. Вычисляемые из props значения обычно считай во время render. Не синхронизируй их через useEffect и вторую копию state. Не добавляй memo/useMemo без причины и не создавай новый тип компонента внутри render. Пример: react-rerender-derived-state-no-effect.md.
5. Server Actions проверяют авторизацию и права независимо от видимости кнопки. Не переноси секреты в браузер и не применяй советы для Next.js Server Components к Vite SPA. Пример: react-server-auth-actions.md.
6. После изменения проверь сборку и исходный сценарий; для интерфейса — узкий экран, клавиатуру и состояния ошибки. Успешный typecheck не равен измерению производительности.

Читай только относящийся к проблеме пример через read_skill_resource, а не весь upstream-react.md и все правила сразу.
